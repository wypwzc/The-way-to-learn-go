### 一、 字符串与编码篇

#### 1. `len(s)` 计算的是字节数，而不是字符数

- **陷阱**：如果你对包含中文或 Emoji 的字符串执行 `len(str)`，返回的是底层 **UTF-8 编码占用的字节数**（一个汉字通常占 3 个字节），而不是字符的个数。
- **看到什么想什么**：当你要限制用户输入的“字数”或遍历文本时，**切忌直接用 `len()` 或下标 `s[i]`**。
- **正确做法**：
  - 求字符数：使用 `utf8.RuneCountInString(s)`。
  - 遍历字符：使用 `for _, r := range s`（会自动将字节解码为 `rune`）。

#### 2. 字符串与 `[]byte` 转换的性能代价

- **陷阱**：在高频场景（如网络收发、日志解析）中频繁进行 `[]byte(s)` 和 `string(b)` 转换，会触发底层内存分配和拷贝。
- **看到什么想什么**：如果在性能敏感的代码中需要零拷贝转换，可以使用 `unsafe` 包（标准库 `strings` 或 `bytes` 内部常用手法，但日常业务中需权衡安全性）。

### 二、 切片 (Slice) 与数组篇

#### 1. 切片共享底层数组的“副作用”

- **陷阱**：通过切片截取（如 `s2 := s1[1:3]`）得到的切片，与原切片**共享底层数组**。如果你修改了 `s2` 中的元素，`s1` 对应的内容也会被悄悄修改。
- **看到什么想什么**：当需要独立修改某个子切片而不影响原数据时，**必须使用 `copy()` 复制一份新切片**，或者使用 Go 1.21+ 的 `slices.Clone()`。

#### 2. `append` 触发底层数组扩容

- **陷阱**：当切片容量（Capacity）不足时，`append` 会自动分配一个更大的底层数组并将旧数据拷贝过去。如果其他变量还在引用旧的底层数组，它们不会被同步更新。
- **看到什么想什么**：在初始化切片时，如果大致知道数据量，**务必预分配容量**（如 `make([]T, 0, len)`），以避免多次内存重新分配。

#### 3. `nil` 切片与空切片的区别

- **陷阱**：`var s []int` 是 `nil` 切片（`s == nil` 为真，`len` 和 `cap` 均为 0）；`s := []int{}` 是空切片（`s == nil` 为假）。
- **看到什么想什么**：在做 JSON 序列化时，`nil` 切片通常会被转成 `null`，而空切片会被转成 `[]`。在声明切片时，如果代表“无数据”，通常直接用 `var s []int` 即可。

### 三、 映射 (Map) 与并发篇

#### 1. Map 不是并发安全的

- **陷阱**：多个 Goroutine 同时读写同一个 Map 会直接触发 fatal error 导致程序崩溃（`fatal error: concurrent map write`）。
- **看到什么想什么**：只要涉及多协程并发操作 Map，**必须加锁**（`sync.Mutex` / `sync.RWMutex`）或使用标准库的 `sync.Map`，或者通过 Channel 进行通信控制。

#### 2. Map 读取不存在的 Key 不会报错

- **陷阱**：访问 Map 中不存在的 Key，不会像 Python 或 Java 那样抛出异常，而是返回该值类型的**零值**（如 `int` 返回 0，`string` 返回 `""`，指针返回 `nil`）。

- **看到什么想什么**：无法仅凭返回值判断 Key 是否存在。**必须使用“逗号表达式”（comma-ok idiom）**：

  Go

  ```
  if val, ok := myMap[key]; ok {
      // Key 确实存在
  }
  ```

#### 3. 不能对 Map 的元素直接取地址

- **陷阱**：`p := &myMap["key"]` 是通不过编译的。因为 Map 可能会在扩容时重新分配内存，导致原先的地址失效。
- **看到什么想什么**：如果需要修改 Map 里的复杂结构体属性，应该先把整个结构体取出来修改，再整体赋回去，或者 Map 的 Value 直接存储**指针**（如 `map[string]*MyStruct`）。

### 四、 接口 (Interface) 与面向对象篇

#### 1. 接口里的“Typed Nil”（类型化空指针）

- **陷阱**：这是 Go 中最经典的坑之一。当一个接口变量持有了具体类型的 `nil` 指针时，**该接口本身并不等于 `nil`**。

- **看到什么想什么**：

  Go

  ```
  var err error // err 是 nil
  var p *MyError = nil 
  err = p       // 此时 err 包含 (type=*MyError, value=nil)，err == nil 为 FALSE！
  ```

  如果函数返回这样的 `err`，调用方用 `if err != nil` 判断会失效，进而导致后续调用引发空指针异常（Panic）。

- **正确做法**：函数内部返回错误时，如果一切正常，直接返回字面量 `nil`，绝不要返回具体类型的 `nil` 指针。

#### 2. 指针接收者与值接收者的实现差异

- **陷阱**：如果为结构体定义了指针接收者的方法（`func (t *T) Method()`），那么只有 `*T` 类型实现了该接口，`T` 类型并没有实现。
- **看到什么想什么**：在设计结构体方法时，如果方法内部需要修改成员变量，或者结构体体积较大，**统一使用指针接收者**，可以避免隐式拷贝和接口实现不一致的问题。

### 五、 闭包与循环变量篇

#### 1. 循环变量捕获陷阱（Go 1.22 之前的老痛点）

- **陷阱**：在 `for i, v := range list` 循环中启动多个 Goroutine 或注册闭包函数时，如果直接使用 `i` 或 `v`，由于所有循环复用同一个变量地址，协程执行时拿到的往往是**循环结束时的最终值**。
- **看到什么想什么**：看到 `for ... range` 里面起 Goroutine 或回调函数，立刻想到要**在块级作用域内重新声明变量**（旧版本写法：`i := i`；在 Go 1.22 及以上版本，语言层面对 `for` 循环变量的作用域做了优化，此问题已大幅改善，但老代码或复杂闭包仍需警惕）。

### 六、 `defer` 与错误处理篇

#### 1. `defer` 的参数在注册时求值

- **陷阱**：`defer fmt.Println(time.Since(start))`，这里的 `time.Since(start)` 是在 `defer` **语句被执行到的时候**就计算好了时间，而不是在函数真正退出时才计算。

- **看到什么想什么**：如果需要延迟计算耗时，应该用匿名函数包裹：

  Go

  ```
  defer func() {
      fmt.Println(time.Since(start))
  }()
  ```

#### 2. `defer` 的执行顺序是先进后出（LIFO）

- **看到什么想什么**：多个 `defer` 像压栈一样，最后注册的最先执行。常用于成对的操作（如打开文件后紧接着写 `defer f.Close()`，多把锁的释放）。

#### 3. 永远不要盲目忽略错误（`_`）

- **陷阱**：写代码图省事写 `file, _ := os.Open(...)` 或 `w.Write(...)` 直接忽略返回值。
- **看到什么想什么**：在网络编程、文件读写、数据库操作中，忽略错误等同于埋下定时炸弹。Go 强调显式错误处理，看到 `err` **必须判断 `if err != nil`**。封装错误时推荐使用 `fmt.Errorf("do something failed: %w", err)` 以保留错误上下文链。

### 七、 并发编程 (Goroutine & Channel) 篇

#### 1. 启动 Goroutine 必须明确它的退出路径

- **陷阱**：随手写 `go func() { ... }()` 却没有控制机制，极易造成 **Goroutine 泄漏**（Goroutine 挂起在阻塞的 Channel 或锁上，永不释放，导致内存缓慢耗尽）。
- **看到什么想什么**：看到 `go` 关键字，立刻思考：*这个协程什么时候退出？怎么通知它退出？（通常通过 `context.Context` 或 `done` Channel）*。

#### 2. 向已经关闭的 Channel 发送数据会 Panic

- **陷阱**：对一个已关闭的 Channel 执行 `ch <- val` 会导致程序崩溃。
- **看到什么想什么**：关闭 Channel 的原则是——**谁发送，谁关闭**。绝不要在接收方关闭 Channel，也避免在多个并发发送方中关闭 Channel。
